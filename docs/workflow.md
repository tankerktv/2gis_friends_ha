# Ветки и публикация

## Схема

| Ветка | Где | Роль |
|---|---|---|
| `development` | GitLab | вся работа; **не зеркалируется** |
| `main` | GitLab | то, что опубликовано |
| `main` | GitHub | зеркало GitLab `main`, сюда смотрит HACS |

Публикуемая ветка называется одинаково с обеих сторон, поэтому зеркало ничего
не переименовывает — схема симметрична.

GitLab — источник истины. GitHub существует только потому, что HACS умеет
ставить исключительно оттуда.

```
development ──merge──> main ──CI──> github/main ──> HACS ──> Home Assistant
   (WIP)              (релизы)
```

Зеркалирование сделано через CI, а не встроенным push-зеркалом GitLab: встроенное
отправляет **все** ветки, а нам нужна только `main` — `development` наружу
попадать не должна. Заодно CI умеет создавать GitHub Releases, чего зеркало не может.

## Обычная работа

```bash
git switch development
# ... правки ...
git commit -am "что сделано"
git push origin development
```

CI на `development` гоняет только проверки. Наружу ничего не уходит.

## Публикация

```bash
git switch main
git merge --ff-only development
git push origin main
```

`--ff-only` осознанно: если fast-forward невозможен, значит в `main` попало
что-то помимо слияний из `development`, и это стоит разобрать руками, а не
заминать merge-коммитом.

Пуш в `main` запускает job `mirror:github`, который отправляет содержимое
в `github/main`.

## Релиз

HACS предпочитает ставить релизы; без них он берёт ветку по умолчанию — работает,
но без версионирования.

1. Поднять версию в `custom_components/twogis_friends/manifest.json`.
2. Слить в `main` как выше.
3. Поставить тег на `main` и запушить:

```bash
git tag v0.1.1
git push origin v0.1.1
```

**Версия в манифесте обязана совпадать с тегом** — job `validate:manifest`
падает, если разошлись. Иначе HACS поставит одно, а HA покажет другое.

Тег уезжает в GitHub через `mirror:github`, а сам Release создаёт уже
**GitHub Actions** — `.github/workflows/release.yml`. Сделано так потому, что
там токен выдаётся job'у автоматически и PAT не нужен. Создавать релиз с двух
сторон нельзя: второй получит `422 Release already exists`.

## То же самое через интерфейс GitLab

Из веба можно пройти весь цикл, не касаясь командной строки.

### Однократная настройка: метод слияния

**Settings → Merge requests → Merge method → `Fast-forward merge`**

Зачем: по умолчанию GitLab создаёт merge-коммит, и после первого же слияния
через интерфейс `main` перестаёт быть простым продолжением `development`. Тогда
`git merge --ff-only` из консоли начнёт отказываться работать, и два способа
публикации станут несовместимы. С `Fast-forward merge` интерфейс ведёт себя так
же, как команда выше, и историю можно вести любым из двух путей.

### Правка кода

Либо локально, либо прямо в вебе: на странице репозитория кнопка **Edit** →
**Web IDE**. Главное — коммитить в `development`, не в `main`.

Пуш в `development` запускает только `validate:*`. Наружу ничего не уходит.

### Публикация

1. **Merge requests → New merge request**
2. Source branch — `development`, target branch — `main` → **Compare branches and continue**
3. Заголовок любой → **Create merge request**
4. **Merge**

Слияние — это пуш в `main`, а он запускает пайплайн, в котором после
`validate:*` отрабатывает `mirror:github`. Отдельно ничего запускать не нужно,
GitHub обновится сам.

Проследить: **CI/CD → Pipelines**, верхняя строка.

### Перезапустить публикацию без новых коммитов

Если `main` уже содержит нужное, а опубликовать не получилось (упала джоба,
не было токена):

* **CI/CD → Jobs** → нужная джоба → **Retry** — перезапуск одной джобы;
* **CI/CD → Pipelines → Run pipeline** → ветка `main` → **Run pipeline** —
  весь пайплайн заново. Здесь же можно подставить переменные вручную, что
  удобно для проверки токена без правки настроек проекта.

### Релиз через интерфейс

1. Сначала поднять версию в `custom_components/twogis_friends/manifest.json`
   и провести её в `main` как выше.
2. **Code → Tags → New tag**, имя `vX.Y.Z`, ветка `main` → **Create tag**.

Тег уедет в GitHub через `mirror:github`, а Release создаст GitHub Actions.
Версия в манифесте обязана совпадать с тегом — иначе проверка упадёт.

## Отдельный README для публики

Если публичный README должен отличаться от рабочего — **не надо** править его
прямо в `main`: каждый следующий merge будет спотыкаться на конфликте.

Вместо этого положи в `development` файл `README.public.md`. Job `mirror:github`
сам подменит им `README.md` при пуше в GitHub. Ветки при этом остаются
идентичными, конфликтов не возникает.

Пока файла нет, шаг подмены ничего не делает.

## Что публикуется, а что нет

Перед первым релизом стоит помнить, что в GitHub уезжает **вся история ветки**,
а не только последнее состояние. Проверка на персональные данные — в
[findings.md](findings.md), раздел про приватность; инструмент для дампов —
`tools/scrub_har.py`.
